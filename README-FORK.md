# ComfyUI-H3-VisionPromptor-Planner — форк с выходами под LongMedia Planner

Форк [benjiyaya/ComfyUI-H3-VisionPromptor](https://github.com/benjiyaya/ComfyUI-H3-VisionPromptor) v1.0.0.
Версия форка: **1.1.6**.

Нода `H3VisionPromptor` получает второй режим — **Planner mode** — и продолжает
работать как локальный (без API-ключей) генератор промптов MiniMax H3 на
нативном VLM-стеке ComfyUI. Режимы переключаются одним тумблером и
взаимоисключимы.

## Назначение

Готовить MultiClip-раскадровки для
[vizart-vj/ComfyUI-MiniMax-H3-LongMedia](https://github.com/vizart-vj/ComfyUI-MiniMax-H3-LongMedia):
текст клипов для **LongMedia Planner** и карточки камер для **LongMedia
Cameras**. Ни Planner, ни Cameras не форкаются и не дорабатываются — форк
только выдаёт совместимые тексты/JSON.

## Быстрый старт

1. Установите форк в `ComfyUI/custom_nodes/` **вместо** оригинального
   ComfyUI-H3-VisionPromptor (node_id совпадает — `H3VisionPromptor`;
   параллельная установка оригинала и форка в одну ComfyUI конфликтует).
   Перезапустите ComfyUI.
2. Поставьте ComfyUI-MiniMax-H3-LongMedia (для приёма выходов).
3. Откройте `example_workflows/h3_vision_promptor_planner.json`, выберите свой
   VLM в CLIPLoader, впишите идею, включите `emit_planner_outputs`.
4. Соедините: `planner_prompt` → вход `multiclip_prompt` Planner'а,
   `global_prompt` → вход `global_prompt` Planner'а (**обязательно**: Planner
   импортирует только `clip_N:`-секции, а константы сцены приписывает к клипам
   именно из `global_prompt` — без этого соединения клипы станут независимыми
   сценами). Включите у Planner'а *Auto Import* (или нажмите *Import*) — тексты
   клипов разъедутся по карточкам.
5. `clip_durations` и `camera_params` — контрольные значения: длительности
   выставьте в карточках Planner'а вручную (текстовый импорт длительности
   Planner игнорирует), карточки камер перенесите в Cameras вручную (у Cameras
   пока нет текстового импорта — JSON подготовлен так, чтобы при появлении
   такого входа его можно было подать как есть).

## Управление режимами

| | `emit_planner_outputs = false` | `emit_planner_outputs = true` |
|---|---|---|
| Активные выходы | `prompt`, `vision_context` | `planner_prompt`, `planner_prompt_ru`, `global_prompt`, `clip_durations`, `camera_params`, `reference_images_status` |
| Неактивные выходы | 6 planner-сокетов скрыты (JS) и возвращают `""` | `prompt`/`vision_context` затемнены (JS) и возвращают `""` |
| `debug` | живой (как в оригинале) | живой (JSON плана, бюджеты токенов, **сырой ответ модели**, warnings) |
| Поведение | байт-в-байт оригинал (проверено тестом против исходного пакета) | vision-проход → planner-проход → перевод → сборка выходов |

Техническое ограничение UI: ComfyUI адресует выходы **по индексу слота**,
поэтому «физически» удаляются только хвостовые planner-сокеты (режим false);
головные сокеты `prompt`/`vision_context` в planner-режиме остаются на месте,
но визуально погашены и всегда пусты. Значения выходов переключаются на
сервере в любом случае — «случайно подключить не то» невозможно.

## Соответствие правилам мультиклипа LongMedia (v1.1.6)

**Задача аудита:** сверить генерацию ноды с правилами репозитория
LongMedia (docs/MULTICLIP_PROMPTING_GUIDE.md, PROMPTING_MULTICLIP.md,
SYSTEM_PROMPT_MULTICLIP_CAMERAS.md, AUDIO_MODES_GUIDE.md).

**Вердикт:** структурно всё было верно (формат импорта `clip_N:`,
GLOBAL=константы / CLIPS=изменения, запрет камерной лексики, наследование
состояния между клипами, действия через границы, позитивные формулировки) —
но три места толкали модель к «независимым клипам»:

| Правило репо | Было | Стало (v1.1.6) |
|---|---|---|
| «Each next clip should continue from the state created by the previous clip» | одна строка в контракте — против креативного блока «alternate the energy between neighbouring clips» | выделенный блок CONTINUITY: clip_1 устанавливает ситуацию, «Never reset the scene», стабильные местоимения, запрет прыжков в другое место/время |
| Рекомендованные глаголы: continues, keeps moving, gradually, slowly, **the movement develops**, **the same action continues**, reaches, begins, moves closer, transitions into | список был укорочен; креативный блок запрещал «опираться на continues/reaches два клипа подряд» | полный список в контракте; стандарты прямо разрешают эти глаголы — «варьируйте предложения, а не сам закон» |
| Global Prompt владеет константами (свет/атмосфера) | креативный блок требовал «never repeat the same dominant lighting condition in adjacent clips» | мир ЭВОЛЮЦИОНИРУЕТ прогрессивно (сумерки сгущаются в ночь); константы живут в GLOBAL |
| `<Audio k>` — семантические адресации (audio-reactive, lip-sync) | отсутствовала | условное правило: если пользовательское сообщение сообщает о подключённых аудио — использовать `<Audio k>`; lip-sync описывать семантически, без фонетики |
| Потеря GLOBAL (модель не выдала секцию / юзер не подключил) | тихий warning в разборе плана | громкий warning + `global_prompt_chars` в debug: константы не дойдут до Planner → клипы как независимые сцены |

**Почему это критично:** Planner импортирует из `multiclip_prompt` ТОЛЬКО
секции `clip_N:` (всё вне их выбрасывается), а `global_prompt` приписывает
к каждому клипу сам в рантайме (join). Поэтому:

- `planner_prompt` → вход `multiclip_prompt` Planner'а;
- `global_prompt` → вход `global_prompt` Planner'а — **обязательное
  соединение: без него константы (идентичность/окружение/стиль) исчезают, и
  клипы станут независимыми сценами даже при идеальном плане**.

**Мотивы (expressive) теперь работают по тому же закону:** «стержень мира»
(world spine — 2 ингредиента на весь план) обязан присутствовать и развиваться
в каждом клипе; каждый клип добавляет «бит» — свой вклад в развитие той же
сцены. Раньше 2 независимых ингредиента на клип → соседние клипы
переодевали мир с нуля.

**Про модель 4B:** «независимость» клипов была не из-за Qwen3-VL-4B-Instruct
— модель честно выполняла противоречивый промпт. 4B тянет трёхсекционный
контракт уверенно; Qwen3-VL-8B-Instruct пригодится, если понадобится больше
дисциплины в JSON-карточках камер и длинных планах (16 клипов) — ставится
так же (family `qwen`, ChatML и think-подавление подхватятся сами), но для
непрерывности замена модели не требовалась.

## Референс-изображения: только якоря, без «На фото изображено…» (v1.1.7)

**Симптом, который это чинит:** подключаете ref-изображение, пишете в идее
«с <image_0> взять лицо и прическу» — а в GLOBAL при любой идее оказывается
«На фото изображено…» и полное vision-описание рефа (фон, поза, «кухня»,
позы «смотрит в камеру»). Клипы при этом остаются нормальными.

**Причина:** полный vision-дамп подаётся в user-сообщение как «Reference
image analysis», но контракт не содержал **ни одного правила** о том, что с
этим дампом делать. Путь наименьшего сопротивления для 4B-модели — скопировать
его в GLOBAL (который просит «subject identity and appearance»). Хуже: дефолтный
пресет `detailed_subject_scene` сам просил VLM описать «(5) camera
framing/shot size» — лексику, запрещённую контрактом. И нотации не совпадали:
вы пишете `<image_0>` (0-based слоты ComfyUI), а контракт и LongMedia ждут
`<Picture 1>` (1-based) — модель не связывала вашу фразу с дампом.

**Фикс v1.1.7 — три уровня защиты:**

1. **Контракт** (`planner_system.txt`): новый блок REFERENCE IMAGES — анализ
   есть RAW MATERIAL («сырьё»), а не контент: не копировать, не пересказывать,
   не упоминать; извлекать **только** атрибуты, которые идея явно просит взять
   с картинки («take the face and hairstyle from <Picture 1>» → GLOBAL несёт
   ровно эти якоря как собственные константы видео); прямой запрет
   фото-лексики («the photo shows», «in the image», «posing», «looking at
   the camera», «on the left side of the frame»…); GLOBAL описывает константы
   **видео**, а не исходное фото; маппинг нотаций: `<image_0>` = `<Picture 1>`,
   `<image_1>` = `<Picture 2>`.
2. **Промпты проходов:** заголовок vision-блока в user-сообщении теперь
   «RAW MATERIAL for identity anchors ONLY … never describe the photo itself»
   + маппинг `<image_0> == <Picture 1>`; системный промпт vision-прохода и
   пресеты `vision_presets.json` запрещают VLM описывать артефакты фотографии
   (no framing / shot type / ориентация / позы) — дамп на входе уже чище.
3. **Детерминированный скраббер** `planner_mode.scrub_photo_meta()` — страховка,
   если модель всё же протащит дамп: предложения с явными отсылками к
   source-картинке («the reference image», «as shown in the image», RU
   «на фото изображено») удаляются из GLOBAL, клипов и RU-зеркала; generic
   фото-лексика («the photo shows») удаляется только из GLOBAL — в клипах
   фотография может быть легитимным предметом сюжета («она поднимает старую
   фотографию»), там она остаётся с warning'ом. Метки `GLOBAL:`/`clip_N:` и
   `<Picture k>` не трогаются; чистый текст проходит байт-в-байт.

**Диагностика:** debug несёт `photo_meta_scrubbed` — сколько предложений
вырезано (0 = модель соблюдает контракт), плюс warnings с примерами
вырезанного. Меняйте seed, если вырезано слишком много.

## Творческое усиление планов (v1.1.5, переработано в v1.1.6)

**Симптом, который это чинит:** планы генерируются корректно, импортируются
без ошибок — но читаются как шаблон: одинаковые конструкции «the subject
continues moving…» из клипа в клип, одна и та же световая атмосфера,
карточки камер-близнецы, никакой выдумки. «Пресно».

**Причина:** контракт planner-режима — это десятки строк правил и запретов
(секции, бюджеты слов, запрещённая камерная лексика) и ни одной строки про
яркость. Instruct-модели на таком промпте играют в максимально безопасного
ученика: шаблонная проза, повторяющиеся глаголы (continues / moves /
reaches), один свет на весь ролик. Добавьте фиксированный seed и невысокую
температуру — и каждый запуск будет одинаково пресным.

**Фикс v1.1.5 — два новых виджета** (в самом низу панели, порядок старых
виджетов не тронут — воркфлоу v1.1.2/v1.1.4 грузятся без правок):

| Виджет | Значения | Что делает |
|---|---|---|
| `creative_boost` | `off` / `standard` / `expressive` (default **standard**) | `off` — без креативных блоков (только встроенный контракт); `standard` — в системный промпт добавляется блок CREATIVE WRITING STANDARDS, переписанный в v1.1.6 в логике continuity-first (конкретные существительные вместо общих прилагательных, поведение света, микрособытия, «варьируйте прозу, а не мир», «одно запоминающееся изображение на клип»); `expressive` — плюс сюрреальные образы, микро-арка «вопрос→ответ», правило «соседние карточки камер отличаются минимум в двух полях» и **мотивные ингредиенты** (стержень мира + биты) |
| `style_directive` | строка (default пусто) | ваш бриф — жанр/настроение/стиль/референсы, передаётся в planner-проход дословно при любом уровне. Пример: «дождливый неонуар, меланхолия, цвета Вонга Карвая» |

**Мотивные ингредиенты (expressive):** узел детерминированно (по seed)
выбирает из встроенных пулов «стержень мира» (world spine — 2 общих
ингредиента на весь план: свет/атмосфера/фактуры/цвет) и по одному «биту»
на клип (движение мира/сторибиты — вклад этого клипа в развитие сцены).
Стержень обязан жить и развиваться в каждом клипе — это правило репо
LongMedia «Global Prompt описывает константы» на уровне ингредиентов.
Ингредиенты — не чек-лист: модель вплетает их незаметно, не цитируя
дословно. Тот же seed — те же ингредиенты; новый seed — новое творческое
направление. Видны в debug (`motif_hints`: `world` + `clips`).

**Плотность текста:** expressive использует более плотную полосу бюджетов
слов (58 + 1.75×сек вместо 45 + 1.4×сек) — стандартные клипы 8–15 с
вырастают с 56–66 до 72–84 слов (всё ещё внутри контракта 50–90), потолок
250 слов не меняется — 16×150 с-планы остаются в токен-бюджете 8192.

**Перевод RU** при любом уровне кроме `off` получает заметку «ХУДОЖЕСТВЕННАЯ
ТОЧНОСТЬ»: перевод обязан сохранить образность, а не выхолащивать её до
нейтрального пересказа.

**Гарантии:** формат вывода не менялся ни на йоту — три секции, клипы,
JSON камер; `off` не добавляет ничего сверх встроенного контракта (сам
контракт — версионируемый файл: v1.1.6 усилил в нём правила непрерывности
по аудиту выше, поэтому «байт-в-байт к v1.1.4» больше не заявляется —
заявляется «off = контракт без креативных блоков», что и тестируется);
`custom_system_prompt` не обогащается фантазией принудительно — только
встроенный промпт; в legacy-режиме оба виджета игнорируются. Креативные
стандарты v1.1.6 переписаны в логике **continuity-first**: «варьируйте
прозу, а не мир» — раньше блок просил чередовать энергию/свет между
соседними клипами, что противоречило правилам непрерывности репо.

**Советы по сэмплеру:** для разнообразия ставьте temperature **0.6–0.8**,
top_p 0.9–0.95 (раньше мы советовали 0.3–0.5 ради стабильности — теперь
стабильность держит контракт, а фантазию подкармливает промпт), и меняйте
seed между прогонами: при expressive новый seed = новые мотивы на каждый
клип.

## Детекция MiniMax-H3 энкодера (важно, v1.1.4)

**Симптом, который это чинит:** файл вида `qwen3vl_32b_minimax_h3_*`
(например `qwen3vl_32b_minimax_h3_nvfp4_awq.safetensors`) в `text_encoder` —
и вместо плана либо «точки» (оригинальный режим), либо «пустышка»/
бесконечные запятые в `raw_planner_answer` (planner-режим),
`planner_seconds` при этом ~4 минуты.

**Причина (найдена по исходникам ComfyUI):** это НЕ инструктивная VLM, а
**кондишнинг-энкодер MiniMax H3** — Qwen3-VL-32B, обрезанный до 50 слоёв,
без финальной LayerNorm, обученный отдавать hidden-состояния для
DiT-видеомодели. ComfyUI детектирует его по весам как `QWEN3VL_32B` и
роутит на `comfy.text_encoders.minimax.MiniMaxH3Tokenizer`, который
**принципиально не применяет chat-шаблон** (докстринг: «The H3 presentation
is NOT chat-templated») и игнорирует `skip_template`. Класс-имена при этом
не содержат «qwen», поэтому наша детекция семейства относила его к
`generic` — и промпт уходил в модель сырым текстом без ChatML. Think-
подавитель v1.1.3 в этом случае физически не мог сработать (он активен
только для family=`qwen`), а старое debug-поле `thinking_suppressed: true`
показывало запрошенный флаг, а не фактический.

**Фикс v1.1.4:**

- `detect_family` собирает больше сигналов (вложенные объекты
  `SD1ClipModel`/`SD1Tokenizer` по ключу `clip_name`, включая
  `MiniMaxH3Tokenizer`/`MiniMaxQwen3VL`/ключ `qwen3vl_32b`) и возвращает
  новое семейство **`minimax_h3`** — приоритет выше «qwen», т.к. сигналы
  H3-энкодера содержат оба слова;
- семейство `minimax_h3` → **мгновенный отказ с понятной ошибкой** в ОБЕИХ
  режимах (до генерации — 32B больше не будет жечь минуты на мусор);
  единственное осознанное отступление от «legacy байт-в-байт»: оригинал в
  этой же ситуации молча выдаёт мусор;
- debug стал честнее: `thinking_suppressed` теперь показывает
  **фактическое** применение подавителя (только для `qwen`), добавлены
  `chat_format` (chatml / gemma-turns / raw) и `family_signals` (что
  именно увидела детекция);
- для family=`generic` (нераспознанный энкодер) — явный warning «промпт
  ушёл сырым текстом без chat-шаблона».

**Что делать:** оставить H3-энкодер для видео-пайплайна MiniMax-H3
(его настоящее применение), а ноде подсоединить **генеративную
инструктивную VLM**: репаки Qwen3-VL 4B/8B Instruct (или
Gemma-3/4-Vision) в `models/text_encoders/`. После замены family станет
`qwen`, ChatML и think-подавление включатся автоматически.

## Подавление размышлений Qwen3 (важно, v1.1.3)

**Симптом, который это чинит:** planner-режим включён, `clip_durations` и
`reference_images_status` заполнены, а `planner_prompt` /
`planner_prompt_ru` / `global_prompt` — пустые строки (или в оригинальном
режиме — «точки» вместо промпта).

**Причина:** Qwen3-модели — «мыслящие»: ответ начинается с блока размышлений
в специальных тегах. ComfyUI подавляет этот режим, добавляя пустой think-блок
сразу после маркера ассистента (так делает сам ComfyUI в своём шаблоне для
qwen3vl). Но наша нода всегда строит промпт вручную, начиная с
`<|im_start|>` — а ComfyUI при таком тексте пропускает свой шаблон
(«умная» защита от двойного оборачивания) и вместе с ним — подавитель
размышлений. В итоге модель тратит весь бюджет токенов на размышления
(на агрессивных квантах — вырождаясь в бесконечные «точки»), видимый ответ
не приходит или обрезан, парсер не находит клипы — и текстовые выходы
пусты.

**Фикс v1.1.3:** во всех трёх проходах planner-режима (vision / план /
перевод) форк сам дописывает пустой think-блок в qwen-шаблон — ровно те же
байты, что использует ComfyUI. Legacy-режим не тронут (байт-в-байт с
оригиналом). Дополнительно debug теперь содержит:

- `raw_planner_answer` — сырой ответ модели ДО очистки (первые 1600 символов)
  и `raw_planner_answer_chars` — полная длина: деградацию видно сразу;
- `raw_translate_answer` — то же для прохода перевода;
- `use_default_template` и `thinking_suppressed` — фактические флаги;
- явный warning, если клики не спарсились: «planner answer yielded no
  parseable clip sections — … inspect raw_planner_answer».

**Диагностика через Previewer на `debug`** — если «пустышка» повторится,
подключите `debug` к Previewer: в `raw_planner_answer` будет видно, что
модель вернула на самом деле (пустоту, точки, мусор или неверный формат).
Если и после подавления размышлений модель вырождается — дело в кванте
(MRFP4/4-бит агрессивен), попробуйте Q4_K_M/Q5 или другой репак.

## Входы (изменения относительно оригинала)

- **`emit_planner_outputs`** (BOOLEAN, default false) — переключатель режима.
- **Трёхуровневая модель длительностей (v1.1.2+).** Три виджета делают
  разные вещи:

  | Виджет | Диапазон | Роль |
  |---|---|---|
  | `duration` | 4–15 с | legacy: длина одного видео; planner: **цель одного клипа** (используется при `clip_duration = 0`) |
  | `clip_duration` | 0–150 с (`0` = авто) | planner: прямое задание **цели одного клипа** — снимает потолок 15 с, до лимита LongMedia в 150 с на клип |
  | `total_duration` | 8–2400 с | planner: **общая длина ролика** — не ограничена 15 с никак |

  В planner-режиме цель клипа = `clip_duration`, если он > 0, иначе `duration`;
  `clip_count = ceil(total / цель)`, clamp 2–16 клипов (лимиты LongMedia),
  каждый клип ≤ 150 с; распределение — равномерное, остаток — в последний
  клип. Длительности считаются арифметикой, а не VLM. Примеры: 24 с / цель 8 с
  → 3×8 с; 60 с / цель 30 с → 2×30 с; 2400 с / цель 150 с → 16×150 с; 2400 с /
  цель 15 с → счёт 160 → clamp 16 → длительности вырастут до 150 с с warning.
  Для длинных клипов (> ~15 с) форк дополнительно выдаёт VLM’у явные
  словесные бюджеты на клип (45 + 1.4×сек, clamp 50–250 слов; expressive:
  58 + 1.75×сек) и масштабирует оценку токенов — нарратив вытягивается по
  длине клипа, а не остаётся «коротким стандартным».
- **Творческое усиление (v1.1.5+):** два хвостовых виджета — `creative_boost`
  (off / standard / expressive, default standard) и `style_directive`
  (ваш бриф). Подробности — в секции «Творческое усиление планов» выше.
- **Размещение виджетов (важно, v1.1.1+).** Все новые входы — `optional`
  и рендерятся **в самом низу панели ноды** (после `extra_instructions` /
  `custom_system_prompt`), а не рядом с `duration`. Причина: ComfyUI
  применяет `widgets_values` сохранённого воркфлоу **позиционно** (порядок
  виджетов = сначала required-входы, потом optional). Чтобы воркфлоу,
  сохранённые с оригинальной нодой, загружались без искажений, порядок
  виджетов оригинала должен оставаться точным префиксом — новые виджеты
  тогда просто берут дефолты (false / 24.0 / 0.0 / standard / ""). В v1.1.0
  входы были вставлены в середину списка: `seed`, `"randomize"`, `temperature`, `top_p`,
  `max_tokens` сдвигались на чужие виджеты — отсюда ошибки «Ввод вне
  диапазона» (temperature 8.4 > 2, top_p 4096 > 1, total_duration =
  огромное число-семя, max_tokens 0 < 256, vision_mode «randomize») при
  загрузке старых воркфлоу. Если вы сохраняли воркфлоу в сломанной v1.1.0 —
  перепоставьте planner-виджеты вручную один раз.
- `variants` в planner-режиме форсируется в 1 (варианты сломали бы формат
  импорта) — в debug пишется предупреждение.
- Бюджет токенов planner-прохода форк считает сам (клипы + глобал + JSON
  камер, с масштабированием под длинные клипы), независимо от виджета
  `max_tokens` (clamp 2048..8192; фактические значения — в debug).
- Остальные входы без изменений. Vision-проход по референсам работает как в
  оригинале; `<Picture k>`-метки вплетаются в тексты клипов.

## Выходы planner-режима

1. **`planner_prompt`** — секции `clip_1:` … `clip_N:` (2–16), по одной
   на клип, **без камерной лексики** (ею владеет Cameras; в клипах — только
   сцена/действие/континуити). Диалоги `<d>[Russian] … </d>` разрешены и
   проходят нетронутыми. Формат гарантированно импортируется парсером
   Planner'а: (а) форк испускает только «голые» метки `clip_N:`; (б) строки
   тела, начинающиеся с `Clip N …`, автоматически нейтрализуются (иначе парсер
   LongMedia принял бы их за новые заголовки и тихо испортил импорт); (в)
   кросс-проверка парсером-двойником включена в тесты.
2. **`planner_prompt_ru`** — русское зеркало того же плана: `GLOBAL:` +
   `clip_N:` (второй проход перевода; метки, `<d>`-диалоги и `<Picture N>`
   сохраняются байт-в-байт; температура перевода понижена до 0.3). Глобал
   живёт внутри RU-выхода — отдельного седьмого выхода нет.
3. **`global_prompt`** — константа сцены для одноимённого входа Planner'а
   (импортёр `multiclip_prompt` преамбулу отбрасывает, поэтому глобал —
   отдельный провод).
4. **`clip_durations`** — JSON-массив длительностей каждого клипа
   (`[8.0, 8.0, 8.0]`). Чек-лист для карточек и задел на будущий умный импорт.
   Если модель выдала другое число клипов, чем план, — длительности
   пересчитываются по фактическому числу (сумма = total), см. debug.
5. **`camera_params`** — JSON-массив карточек **строго по 13 ключам карточки
   LongMedia Cameras**: `clip_id, clip_name, shot_size, rig, camera_body,
   lens, stabilization, movement, speed, transition_type, space_relation,
   entity_continuity, transition_to_next` (последнему клипу `false`).
   Значения — только из словаря Cameras (13 shot size, 25 rig, 29 body, 32
   lens, 10 stabilization, 35 movement, 8 speed, 4 transition, 3 space, 3
   entity ≈ 160 значений с семантическими описаниями, скопированными из
   серверных словарей LongMedia v0.6.40). Знания инъектируются в системный
   промпт генератора; невалидное значение форк нормализует (fuzzy) или
   заменяет дефолтом с предупреждением в debug. Словарь автономно лежит в
   `py/camera_knowledge.py` — LongMedia не импортируется; при изменении его
   словаря файл нужно зеркально обновить.
6. **`reference_images_status`** — `{"images_connected": true, "count": 2,
   "slots": ["image_0","image_1"]}` (или `false/0/[]`). IMAGE-тензоры путей не
   несут, поэтому выход — маркер наличия/количества, а не пути. Поданные на
   генерацию картинки пользователь подаёт и на генерацию видео.

## Как работает генерация

Один planner-проход с жёстким контрактом секций:

```
=== GLOBAL ===
<константа сцены, 40–70 слов>

=== CLIPS ===
clip_1: … clip_N:            (по 50–90 слов, без камер)

=== CAMERAS ===
[{…}, {…}, {…}]              (JSON, N карточек)
```

Форк расщепляет ответ детерминированно; фоллбеки с предупреждениями: нет
GLOBAL → `global_prompt=""` (клипы остаются самодостаточными); нет CAMERAS →
`"[]"`; нет `clip_N:` → все planner-выходы пустые + ошибка в debug. Штатный
`post_processor.finalize()` в planner-режиме полностью обходится — его
sanitize по H3-заголовкам и авто-дописывание `overall_soundscape: N/A`
исказили бы мультиклип-текст. Вместо него — лёгкий клинер (снятие
code-fences и think-блоков, ничего не добавляет и не отрезает).

Системные промпты: `prompts/planner_system.txt` (контракт + полный словарь
камер через плейсхолдер `{{CAMERA_KNOWLEDGE_BLOCK}}`) и
`prompts/planner_translate.txt`. Оба хотрелоадятся с диска; правьте без
перезапуска. `custom_system_prompt` в planner-режиме по-прежнему заменяет
встроенный системный промпт целиком (тогда словарь камер не инъектируется).

## Известные ограничения

- Камеры: перенос карточек в ноду Cameras — руками (текстового входа у Cameras
  нет; JSON готов к будущему импорту).
- Длительности: карточный импорт Planner'а игнорирует длительности из текста —
  выставляйте по `clip_durations`.
- RU-зеркало не проходит дефузинг строк-«псевдозаголовков» (для русского текста
  грамматика `clip/shot+N` практически не встречается); канал импорта — EN
  `planner_prompt`.
- Параллельная установка оригинала и форка в одну ComfyUI не поддерживается
  (одинаковый node_id `H3VisionPromptor`) — это цена drop-in совместимости
  старых воркфлоу.
